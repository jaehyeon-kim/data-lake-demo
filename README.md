# data-lake-demo

Data lake demo using change data capture (CDC) on AWS.

- [Data Lake Demo using Change Data Capture (CDC) on AWS – Part 1 Local Development](https://jaehyeon.me/blog/2021-12-05-datalake-demo-part1/)
- [Data Lake Demo using Change Data Capture (CDC) on AWS – Part 2 Implement CDC](https://jaehyeon.me/blog/2021-12-12-datalake-demo-part2/)
- [Data Lake Demo using Change Data Capture (CDC) on AWS – Part 3 Implement Data Lake](https://jaehyeon.me/blog/2021-12-19-datalake-demo-part3/)

## Architecture

![architecture](./images/architecture.png)

1. Employing the [transactional outbox pattern](https://microservices.io/patterns/data/transactional-outbox.html), the source database publishes change event records to the CDC event table. The event records are generated by triggers that listen to insert and update events on source tables.
2. CDC is implemented in a streaming environment and [Amazon MSK](https://aws.amazon.com/msk/) is used to build the streaming infrastructure. In order to process the real-time CDC event records, a source and sink connectors are set up in [Amazon MSK Connect](https://aws.amazon.com/msk/features/msk-connect/). The [Debezium connector for PostgreSQL](https://debezium.io/documentation/reference/stable/connectors/postgresql.html) is used as the source connector and the [Lenses S3 connector](https://lenses.io/blog/2020/11/new-kafka-to-S3-connector/) is used as the sink connector. The sink connector pushes messages to a S3 bucket.
3. [Hudi DeltaStreamer](https://hudi.apache.org/docs/hoodie_streaming_ingestion/#hudi-streamer) is run on [Amazon EMR](https://aws.amazon.com/emr/). As a spark application, it reads files from the S3 bucket and upserts Hudi records to another S3 bucket. The Hudi table is created in the AWS Glue Data Catalog. The tool was renamed to Hudi Streamer in later Hudi releases, so the link above points at its current documentation page; the class name in this repository is still `org.apache.hudi.utilities.deltastreamer.HoodieDeltaStreamer`.
4. The Hudi table is queried in [Amazon Athena](https://aws.amazon.com/athena/) while the table is registered in the AWS Glue Data Catalog.
5. Dashboards are created in [Amazon Quicksight](https://aws.amazon.com/quicksight/) where the dataset is created using Amazon Athena.

## Repository layout

The folders are components of one pipeline, not separate examples. The three posts are stages of the same build, and the table below says which stage uses which folder.

| Path | Used by | What it holds |
|---|---|---|
| [data/sql](data/sql) | part 1 and part 2 | Four SQL files that create the `datalake` schema, load the Northwind tables, and add the `cdc_events` outbox table with the triggers that fill it. Part 1 runs them through the Postgres container, part 2 runs them against Aurora. |
| [data/load](data/load) | part 2 | A Typer command line tool that connects to the Aurora database, creates the `datalake` schema, and runs the three SQL scripts in `data/sql` against it. |
| [docker-compose.yml](docker-compose.yml) | part 1 | The local stack: `debezium/postgres:13`, Confluent Platform 6.2.1 (ZooKeeper, broker, Schema Registry, Connect, Control Center, REST Proxy). It mounts `data/sql` into the Postgres container and builds the Connect image from `connector/local`. |
| [connector/local](connector/local) | part 1 | The Docker version of the two connectors. A Dockerfile that adds the Debezium PostgreSQL connector 1.7.1 and the Lenses stream-reactor S3 connector 3.0.0 to the Connect image, the connector JSON configurations, and `setup.sh` with the curl commands that register them. |
| [connector/msk](connector/msk) | part 2 | The MSK Connect version of the same two connectors, as `.properties` files. The database host, user and password in `source-debezium.properties` are placeholders that have to be filled in. |
| [infra/vpc](infra/vpc) and [infra/state](infra/state) | part 2 | CloudFormation templates from [cloudonaut.io](https://templates.cloudonaut.io/en/stable/) for the VPC, the bastion hosts, the KMS key, the Secrets Manager secret and the Aurora database. Part 2 links `infra/state/rds-aurora.yaml`. |
| [infra/main/msk.yaml](infra/main/msk.yaml) | part 2 | The MSK cluster, its security group, its CloudWatch log groups and the IAM role that MSK Connect assumes. |
| [infra/main/emr.yaml](infra/main/emr.yaml) | part 3 | The EMR cluster that runs DeltaStreamer. Its default release label is `emr-6.4.0`. |
| [kafka-ui](kafka-ui) | part 2 helper | A one service compose file that runs `provectuslabs/kafka-ui` against the MSK cluster with `AWS_MSK_IAM` authentication. It is a convenience for watching the topic, not a step in the pipeline. |
| [hudi](hudi) | part 3 | The DeltaStreamer property files, the Avro schema, `execute.sh` with the two `spark-submit` commands and the `aws emr add-steps` call, and `steps/cdc-events-simple.json`. |

## Values that are hard coded

The repository was written for one AWS account and nothing reads these from a variable, so a reader has to edit them before running anything.

- The S3 bucket name `data-lake-demo-cevo` appears in `connector/local/sink-s3.json`, `connector/msk/sink-s3-lenses.properties`, `connector/msk/sink-s3-confluent.properties`, both files under `hudi/config`, `hudi/execute.sh` and `hudi/steps/cdc-events-simple.json`.
- The EMR cluster id `j-31A980N14RJY9` in the `aws emr add-steps` call at the end of `hudi/execute.sh`. It is the cluster id from the original run and will not exist in another account.
- The Hive JDBC address `jdbc:hive2://10.100.22.160:10000` in both `hudi/config/cdc_events_deltastreamer_s3.properties` and `hudi/config/cdc_events_deltastreamer_s3-simple.properties`. It is the private IP address of the master node of that EMR cluster.
- The region `ap-southeast-2` in `connector/local/sink-s3.json`, both sink files under `connector/msk`, and the `aws emr add-steps` call in `hudi/execute.sh`.
